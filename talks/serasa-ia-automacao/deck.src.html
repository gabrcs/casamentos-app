O ponto de partida

A pergunta errada é "o que a IA consegue fazer aqui?"

A pergunta certa é: neste processo, o que é decisão e o que é digitação?

Automação com IA é 80% desenho de processo e 20% modelo. Quem inverte essa conta entrega uma demo bonita que ninguém usa em produção.
NOS PRÓXIMOS 25 MIN mapear→ decidir→ humano na alça→ levar para produção→ um caso real
O método

Quatro passos e quatro formas. É só isso.

1Desenhe o fluxo como ele acontece hoje, sem melhorar nada. Entreviste quem executa: a versão do gerente é a oficial, a de quem executa é a real.
2Uma caixa por ação, um losango por decisão. Na dúvida, é decisão — decisão escondida dentro de ação é onde a automação quebra depois.
3Tabele cada caixa: entrada, saída, dono, volume/mês, taxa de exceção, custo do erro. Sem os dois últimos, o passo 4 é chute.
4Volte ao desenho e pinte cada caixa: código, IA ou humano. O fluxo pintado é a arquitetura.
A notação inteira
Por que fluxograma e não texto

Processo em texto esconde decisão. Em fluxograma, decisão tem forma própria — e é exatamente onde você vai escolher entre código, IA e humano. O desenho não é documentação, é a ferramenta de decisão.

Como ler

Linha 1 é digitação → código. Linhas 2 e 4 são decisão ambígua com erro tolerável → IA. Linha 3 é regra fixa → código, nunca LLM. Linha 5 é julgamento irreversível → humano. O mapa dá a arquitetura antes de você escrever uma linha.

Automação de processos com IA02 · Decidir
O padrão mais útil, na prática

Escalonamento por confiança — são doze linhas

triagem.py
# o schema é o contrato: sem ele não há limiar nem log class Triagem(BaseModel): categoria: Literal["cobranca", "fraude", "cadastro", "outro"] confianca: float # 0-1, exigido no prompt justificativa: str # 1 frase — vai para o log faltou_contexto: bool # o caminho explícito de "não sei" r = classificar(ticket) # saída estruturada, não texto livre if r.faltou_contexto or r.confianca < LIMIAR: fila_humana.enfileirar(ticket, sugestao=r) # COM a sugestão else: rotear(ticket, r.categoria) registrar(ticket.id, r, modelo=MODELO, prompt_v=PROMPT_V)

O limiar sai do eval

Rode os casos, veja onde o acerto cai, escolha ali. Começamos em 0.85 — o ponto em que o erro confiante zerou.

Escalone com a sugestão

Fila que chega em branco custa o mesmo que não ter automação. Com categoria sugerida + justificativa, o humano confirma em segundos.

Meça a taxa de escalonamento. Subiu? Mudou o contexto ou apareceu categoria nova — não é o modelo piorando.

O detalhe que quase todo mundo esquece

Sem faltou_contexto, o modelo nunca diz "não sei" — ele chuta com confiança alta. "Não sei" precisa ser uma saída válida e explicitamente permitida no prompt, senão você mediu confiança de um modelo que não tem como discordar de si mesmo.

Automação de processos com IA03 · Humano na alça
O anti-padrão que passa em toda auditoria

Se o humano aprova 400 itens por dia, não existe humano na alça — existe um ritual de aprovação

Três perguntas para saber se o checkpoint é real

1. O revisor tem tempo e informação suficientes para discordar?

2. Existe registro de quando ele discordou? Taxa de rejeição de 0% é alarme, não é qualidade.

3. Se a revisão por amostragem daria o mesmo resultado, a revisão item a item é teatro — e está te custando uma pessoa.

O lado regulatório

A LGPD, art. 20 garante ao titular o direito de solicitar revisão de decisões tomadas unicamente com base em tratamento automatizado que afetem seus interesses.

Em serviço financeiro isso não é rodapé jurídico: é o que define quais etapas podem ser 100% automáticas — e obriga rastro de qual versão do modelo decidiu o quê, quando.

Consequência prática: desenhe o log de decisão junto com o fluxo, não depois da primeira solicitação de revisão.

O que separa piloto de produção

Todo piloto tem a camada de modelo. O que quase nenhum tem é orquestração e eval — e são exatamente as duas que decidem se aquilo sobrevive ao terceiro mês.

Automação de processos com IA04 · Ferramentas
O artefato que separa automação de aposta

O eval set é um arquivo. Comece por ele, não pelo prompt.

evals/triagem.yaml  ·  versionado no repo, revisado em PR
# 20 casos REAIS tirados do histórico — não inventados - id: cob-001 entrada: "não reconheço a cobrança de R$ 89,90 no cartão" esperado: { categoria: cobranca, escalona: false } - id: frd-014 entrada: "abriram conta no meu CPF, quero registrar fraude" esperado: { categoria: fraude, escalona: false } # os casos de borda são os que importam: # este é ambíguo de propósito e DEVE escalonar - id: amb-007 entrada: "cobrança que não fiz, acho que usaram meus dados" esperado: { escalona: true }
no CI, bloqueando merge
pytest evals/ --limiar 0.85 # falha = não entra em produção

Os três números

Acerto por categoria — média esconde a categoria que vai mal.

Taxa de escalonamento — o custo humano que você está criando.

Erro confiante — errou com confiança acima do limiar. Este é o número que mata o projeto. Meta: zero.

Vinte casos bastam

Não espere ter mil. Vinte casos reais, sendo cinco de borda, já pegam quase toda regressão. O eval que existe vale infinitamente mais que o eval perfeito que você faria depois.

Os outros dois artefatos

O prompt tem anatomia. E toda decisão deixa rastro.

prompts/triagem.v4.md  ·  sete seções, sempre nessa ordem
## 1. Papel Você tria solicitações de suporte de um bureau de crédito. ## 2. Tarefa Classifique em UMA categoria e informe sua confiança. ## 3. Dados {{ticket}} {{historico_do_cliente}} ## 4. Regras de decisão - Menção a CPF usado por terceiro → sempre fraude. - Valor contestado + suspeita de terceiro → escalone. ## 5. Formato de saída JSON no schema Triagem. Nada fora do JSON. ## 6. Quando NÃO decidir Falta histórico ou cabe em duas categorias → faltou_contexto: true. Não chute. ## 7. Casos de borda <3 exemplos vindos direto do eval set>
o registro de cada decisão  ·  uma linha por execução
{ "ticket": "T-88421", "ts": "2026-07-30T14:02:11Z", "modelo": "<id e versão fixados>", "prompt_v": "4", "entrada": "<hash + referência>", "saida": { "categoria": "fraude", ... }, "confianca": 0.91, "decidiu": "automatico", "revisado_por": null, "revertido_em": null }
Por que exatamente esses campos

modelo + prompt_v = você consegue reproduzir a decisão seis meses depois. decidiu + revisado_por = você responde a uma solicitação do art. 20 da LGPD sem arqueologia. revertido_em = você mede se a supervisão humana está pegando algo — se está sempre null, ou está perfeito, ou ninguém está olhando.

Automação de processos com IA04 · Ferramentas
O portão antes de produção

Doze itens. Desmarcado é risco assumido, não esquecimento.

Eval set no repo, 20 casos, rodando no CI e bloqueando merge.
Versão do modelo fixada. Atualizar é deploy: eval antes, rollback previsto.
Prompt versionado em arquivo e revisado em PR. Não mora em Google Doc.
Saída estruturada com schema validado no código, não texto livre.
Caminho de "não sei" existe, é permitido no prompt e é medido.
Conta feita em código, não pedida ao modelo. Ferramenta > aritmética.
Registro por execução com modelo, versão do prompt e quem decidiu.
Retry e idempotência na orquestração. Reprocessar não duplica efeito.
Custo por execução medido e multiplicado pelo volume do canvas.
Você sabe qual campo de dado sai da empresa — o campo, não a ferramenta.
Undo existe onde o padrão é supervisão. Sem undo, não é supervisão.
Tem dono com nome e data de revisão na agenda. Não nome de squad.
Como usar

Não é lista de boas intenções, é portão de produção. Rode antes de ligar o fluxo, e trate item desmarcado como risco aceito conscientemente — com nome e data ao lado.

Para levar

Três frases e um desafio de uma semana

01Mapeie o processo antes de escolher a ferramenta.
02Automatize o que é digitação. Mantenha o humano onde errar é caro.

Desafio

Escolha um processo que você executa toda semana. Preencha o canvas de uma página. Marque a única linha que é pura digitação. Automatize só ela. Meça. Depois volte para a segunda linha.
